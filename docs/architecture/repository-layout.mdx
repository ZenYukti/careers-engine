# Repository Layout

Careers Engine follows a modular Python project structure. Source integrations, parsers, filtering, employment classification, storage, and publishing are organized into separate components, while tests, documentation, and automation workflows remain independently maintainable.

The project also separates application code from persistent operational data through the [`careers-data`](https://github.com/ZenYukti/careers-data) repository.

## Application Code — `src/careers_engine/`

Find the source here: https://github.com/ZenYukti/careers-engine/blob/main/src/careers_engine

The application package contains the implementation of the aggregation and publishing engine.

| Path | Responsibility |
| --- | --- |
| `sources/` | Retrieves listings from supported upstream sources. |
| `parsers/` | Parses source-specific formats into normalized job records. |
| `models/` | Defines the canonical job model and related types. |
| `filters/` | Applies eligibility rules to collected opportunities. |
| `employment.py` | Infers employment categories from job titles. |
| `company/` | Maintains company branding metadata and logo-resolution logic. |
| `assets/` | Organizes branding assets used by the application. |
| `storage/` | Handles persistent job and workflow state. |
| `pipeline.py` | Coordinates the ingestion pipeline. |
| `config.py` | Centralizes application configuration and environment-derived settings. |

Each component has a defined responsibility, allowing individual parts to evolve without requiring the entire pipeline to be rewritten.

For the complete data flow, see the [Ingestion Pipeline](/architecture/ingestion-pipeline).

## Scripts — `scripts/`

The scripts directory contains the application's executable entry points for operational workflows.

The main entry points are:

- `collect.py`: runs the collection and ingestion process.
- `publish.py`: runs the publishing process.

Keeping these entry points separate makes ingestion and publishing independently executable, both locally and through GitHub Actions.

See the [Running Locally](/getting-started/running-locally) guide for local execution instructions.

## Tests — `tests/`

The test suite validates the behavior of the application's components.

Tests cover areas such as source adapters, parsers, eligibility filtering, employment classification, and other core logic.

The separation of components makes it possible to test parsing and classification rules independently of scheduled workflows or live Discord publishing.

The project uses Pytest for test execution, alongside Ruff for linting and formatting and Mypy for static type checking.

See the [Testing Guide](/developer-guide/testing) for the project's testing workflow.

## Documentation — `docs/`

The documentation is organized by purpose rather than being maintained as one large guide.

| Directory | Purpose |
| --- | --- |
| `getting-started/` | Installation, configuration, local execution, bot setup, and workflow setup. |
| `architecture/` | System design, component responsibilities, and data flow. |
| `developer-guide/` | Instructions for extending sources, logos, and employment rules, as well as contributing and testing. |
| `api/` | Code-level interfaces and component references. |
| `reference/` | Configuration, environment variables, schemas, CLI, and workflow details. |
| `images/` | Diagrams and visual assets used by the documentation. |

The documentation navigation is configured in `docs/docs.json`.

## Automation — `.github/workflows/`

GitHub Actions workflows automate scheduled and manually triggered operations.

The ingestion workflow runs the collection entry point and persists changes to the data repository. The publishing workflow selects unpublished opportunities, delivers them to Discord, and persists publication history.

Keeping orchestration in workflow definitions allows the application logic to remain executable independently of the CI environment.

See the [GitHub Actions guide](/getting-started/github-actions) for setup and execution details.

## Persistent Data — `careers-data`

Persistent operational state lives in the separate [`careers-data`](https://github.com/ZenYukti/careers-data) repository.

| File | Responsibility |
| --- | --- |
| `jobs.json` | Stores normalized job records. |
| `history.json` | Tracks publication history. |
| `queue.json` | Stores manually submitted opportunities for the Queue Opportunity workflow. |

This separation prevents frequently changing generated data from being mixed with application source code. The workflows check out the data repository when they need to read or update its contents.

See [Storage Architecture](/architecture/storage) for the persistence model and the responsibilities of each file.

## Project Configuration

The root configuration files support development, dependency management, and quality checks.

- `pyproject.toml` defines project metadata, dependencies, and tool configuration.
- `uv.lock` records the resolved dependency versions.
- `Makefile` provides convenient commands for development and validation.

These files make the development environment and quality checks easier to reproduce.

## Extending the Repository

When adding functionality, place it in the component that owns the relevant responsibility.

- Add a new upstream integration under `sources/` and its corresponding parser where required.
- Add eligibility behavior under `filters/`.
- Extend employment classification in `employment.py`.
- Add company branding through the existing company registry and asset conventions.
- Add or update tests under `tests/`.
- Update the relevant documentation when behavior or developer workflows change.

Use the [Adding a Source](/developer-guide/adding-source), [Adding an Employment Rule](/developer-guide/adding-employment-rule), and [Adding a Logo](/developer-guide/adding-logo) guides for component-specific instructions.
